## 01:06 — The six encryption levels ([↗](https://www.youtube.com/watch?v=i_T7hNmbgEQ&t=66s))

Let's start with encryption levels. Picture office building. You could lock the front door of the whole building. You could lock one floor, one filing cabinet, or a single folder inside it. Each choice protects against different problems and costs a different amount of effort. Encryption works the same way and the encryption level is how much of the data you scramble in one go. There are six levels to know. Full disk encryption scrambles everything on a drive including the operating system. That's Bit Locker on Windows and File Vault on Mac. Partition encryption scrambles one partition which is a slice of a physical disc. Volume encryption scrambles a volume which is a logical storage unit the operating system mounts as a single drive.

A volume can sit on one partition or stretch across several. File encryption scrambles individual files or folders and the protection travels with the file even when you email it or copy it to a thumb drive. Database encryption scrambles the database itself. Commonly the database files and backups on disk. So a stolen copy of the files is useless. and record encryption scrambles individual records, rows, or even single fields like a social security number column, each with its own protection. Broad levels are easy to roll out and nobody has to think about them. Narrow levels give finer control, but somebody has to manage more keys. A word of warning, full disc encryption only protects a device that's off or locked.

Once you log in, the drive is unlocked and anything running as you, including malware, can read the files. Full disk encryption answers the question, what if someone steals the laptop? It doesn't answer who inside the company can read the data. Here's a quick tip. Match the level to the threat. Stolen laptop points to full disk. Sharing one sensitive file points to file encryption. And a database administrator who shouldn't see card numbers points to record or fieldle encryption because encryption of the database files on disk still shows plain text to anyone who can run a query. ## 03:16 — Data in motion: TLS and IPsec ([↗](https://www.youtube.com/watch?v=i_T7hNmbgEQ&t=196s))

let's talk about data in motion. Everything so far protects data sitting still. Transport encryption also called communication encryption protects data while it travels across a network where anyone along the path could copy it. The tool is an encryption protocol, a published set of rules two systems follow to set up and run an encrypted conversation. Three protocols to recognize. TLS, transport layer security, wraps traffic between a client and a server. It turns HTTP into HTTPS and puts the padlock in your browser. IPSec encrypts traffic at the network layer, so it protects everything between two sites or devices without each app needing to know. It's a favorite for VPNs. And SSH, secure shell, gives you an encrypted command line to remote servers and carry secure file transfer.

Many older protocols send everything as readable plain text, and the fix is almost always the encrypted twin. HTTP becomes HTTPS on port 443. Telnet becomes SSH on port 22. FTP becomes SFTP which runs over SSH also on port 22. And LDAP becomes SFTP which runs over SSH also on port 22. And LDAP becomes LDAP. Version numbers matter too. SSL, the ancestor of TLS, is obsolete and the IETF, the group that writes internet standards, formally banned TLS 1.0 and 1.1 in 2021. TLS 1.2 is still widely used and fine with strong ciphers. TLS 1.3 is the current version, faster and stripped of weak options. United States federal guidance has required government servers to support it since January 2024.

Here's a quick tip. If a scenario shows credentials crossing the network in CLEX, the best answer is nearly always to switch to the encrypted version of the same protocol. Learn those pairs.

## 05:31 — Key exchange and forward secrecy ([↗](https://www.youtube.com/watch?v=i_T7hNmbgEQ&t=331s))

Next, key exchange. You already know the puzzle. Two people who've never met need a shared symmetric key, but anyone could be listening. Key exchange is the family of methods that solves it. It's the first step of the hybrid encryption trick from the last lesson. Now with the details filled in, the classic answer is Diffy Helman. Here's the paint mixing picture. You and a stranger publicly agree on a common yellow paint. Each of you secretly picks a private color and mixes it into the yellow. You swap the mixed buckets in full view of a watching spy. Each of you then adds your own secret color to the bucket you received. You both end up with the exact same fin shade, but the spy who only saw the in between buckets can't unmix paint to recover it.

That final shade becomes your shared key. Modern TLS uses ecdh, which is diffy helman done with elliptic curves using fresh throwaway values every time. Ephemeral means short-lived because each session builds its own key and then forgets it. A thief who steals the server's long-term private key later can't decrypt old recorded sessions. That protection is called perfect forward secrecy. There's one more catch. Plain Diffy Helman has no idea who's on the other end, so an attacker in the middle could run one exchange with you and another with the server. That's why the server proves itself with a certificate and signs part of the handshake. So you know you're mixing paint with the real bank.

The older alternative where the client encrypts a random secret with the server's RSI public key has no forward secrecy which is why TLS1.3 dropped it. Keys can also move out of band through a separate channel like a phone call or a courier instead of inband over the channel you're protecting. The key thing to remember is this key exchange lets strangers build a shared symmetric key without ever sending it. Ephemeral exchanges give you perfect forward secrecy and certificates stop an impostor from sitting in the middle. Now

## 11:57 — Keeping keys safe: TPM and HSM ([↗](https://www.youtube.com/watch?v=i_T7hNmbgEQ&t=717s))

Now let's talk about keeping keys safe. Algorithms are public. So the real secret is the key. A key sitting in a plain file on the server it protects is a gift to attackers. Four tools help. A TPM, a trusted platform module, is a small chip on a laptop or server's motherboard. It stores keys and checks that the machine started in a trusted state. Bit Locker uses it to unlock the drive only if the boot process wasn't tampered with because everything else trusts it. A TPM is a hardware route of trust. An HSM, a hardware security module, is a temperistant appliance, card, or cloud service built to generate, store, and use keys without ever exposing them.

Certificate authorities and banks keep their most sensitive keys in HSM. Think of a vault with a teller window. You can ask for work to be done, but you can never walk off with the contents. A key management system is the service that handles the whole key life cycle. Creating, storing, rotating, controlling access to, and destroying keys. Cloud platforms offer these, often backed by IHSM. And a secure enclave is an isolated protected area inside a processor with its own memory that even the operating system can't read. Phones use one to guard fingerprint data and keys. Enclaves can also protect sensitive work while it runs, which ties to data in use. Then there's key escrow, the safety net.

It means storing a copy of a key with a trusted party or splitting it among several people so it can be recovered if the original is lost, an employee leaves, or investigators legally need access. The trade-off is that you gain recoverability but create another target. You'd escrow encryption keys, not signing keys, because a second copy of a signing key undermines non-repudiation. Here's a quick tip. Match the tool to the story. Drive encryption and boot checks mean TPM. A certificate authority that must never expose its master keys means IHSM. Rotating and auditing many keys means a key management system. And protecting secrets from a compromised operating system means a secure enclave.

## 18:43 — Post-quantum cryptography ([↗](https://www.youtube.com/watch?v=i_T7hNmbgEQ&t=1123s))

Postquantum cryptography isn't named in Compia's published objectives. So don't spend serious study time on this. It's here because it shows why the industry cares so much about key exchange, key length, and agility. A quantum computer uses cubits which exploit quantum physics to take shortcuts on certain math problems. RSI, Diffy Helman, and ECC all depend on problems of that exact kind, easy to do forwards and brutally hard to undo. A large enough quantum computer running Shaw's algorithm could undo them quickly, no matter how long the keys are. Symmetric encryption is in far better shape. Grover's algorithm only speeds up key guessing modestly. So AS 256 stays comfortable. The earthquake is under one building.

Public key crypto, not the whole city. Why act now? Because an attacker can copy your encrypted traffic today, store it, and decrypt it when the machine arrives. That's called harvest now, decrypt later. And it matters most for data that must stay secret for many years. Postquantum cryptography or PquayC means public key algorithms built on math that quantum computers can't shortcut. NIST finalized its first three standards in August 2024. FIPS 203 MLKM handles key exchange. FIPS 204 MLDDSA handles signatures and FIPS 205 SLHDSA is a conservative backup signature built on hashing. Two more are still in progress as of October 2026. HQC, a backup key exchange, was selected in March 2025, but its draft standard hasn't been published, and FNDSA, a compact signature scheme, is still working through approval.

NIST's transition road map, NIST IR8547, is still a draft. It proposes retiring today's 112bit strength public key algorithms after 2030 and disallowing every quantum vulnerable one after 2035. Current browsers already negotiate a hybrid exchange that combines classic X25519 with MLKM. So a flaw in either one doesn't expose your session. The practitioner's lesson is crypto agility building systems so you can swap algorithms through configuration because algorithms do eventually fall. MD5 and SHA1 already did. Here's a quick tip. If a question says quantum computing threatens RSA, remember that bigger RSI keys don't fix it because the underlying math breaks. Bigger keys only help symmetric encryption.
