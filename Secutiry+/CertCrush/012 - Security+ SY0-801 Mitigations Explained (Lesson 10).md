# Security+ SY0-801 Mitigations Explained (Lesson 10)

## 00:00 — Mitigations: the six areas ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=0s))

You've spent several lessons learning who attacks you, how they do it, and where the weak spots hide. Now comes the satisfying part, shutting those doors. Mitigations are the moves that turn a scary threat list into a manageable one, and the exam loves to ask which move is the best fit for a given situation. In this lesson, you'll learn six things. First, hardening and real-world patch management. Second, segmentation, access controls, sandboxing, and deception tools like honeypots. Third, endpoint and device protection from antivirus and EDR to allow lists and mobile device management. Fourth, content filtering and data loss prevention. Fifth, application security and email security, including SPF, DKIM, DMARC, and BIMI, plus operating system tools like group policy and SElinux.

And sixth, how to choose the best mitigation for a described threat. Before we dive in, a quick refresher. A mitigation is a security control, and you already met the full vocabulary of controls earlier. When the exam asks, "What's the best mitigation here?" it's really asking, "Which control of which type fits this situation?" Keep the control types mind. Preventive, deterring, corrective, detective, compensating, and directive. This lesson covers most of the toolkit. Firewalls, network intrusion detection and prevention, and network access control come in the next lesson. Let's start with hardening.

## 01:35 — Hardening and configuration ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=95s))

Hardening means reducing a system's attack surface by turning off, removing, or locking down everything you don't strictly need. A brand new laptop ships with a dozen background services, sample apps, default accounts, and open features, and every one is a door an attacker might try. Hardening is bricking up the doors nobody uses. In practice, you disable unused services and ports, remove default accounts, uninstall software the system doesn't need, restrict permissions to the least access required, and enable security features that ship turned off, like host firewalls and disk encryption. Here's a quick tip. The very first step on any new device is changing the default password. It costs 2 minutes and closes an enormous door.

You don't want to harden every machine by hand. That's where a secure baseline comes in. A documented, approved standard configuration every system of a given type must match. It's the recipe. You rarely write one from scratch. Free hardening guides, like the benchmarks from the Center for Internet Security, give you a ready-made start. Configuration management is the ongoing discipline of building systems to that baseline and catching the drift as people tweak settings over time.

## 02:52 — Patch management and priorities ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=172s))

Now, patch management. A patch is a vendor-supplied fix for a bug or vulnerability. Once a fix is public, the flaw it fixes is public, too. Attackers read the same release notes you do, and the race is tightening. Verizon's 2026 Breach Report found that exploiting vulnerabilities had overtaken stolen credentials as the most common way into a breach, and that the median time to fully patch a flaw had grown to 43 days, up from 32. The gap between patch released and patch applied is where breaches live. Patch management is the structured process of finding, testing, and deploying fixes. Notice the middle word. Testing. A patch can break things if you slap it on carelessly, so the life cycle runs like this.

Identify which systems need which patches, prioritize by severity and exposure. Test in a staging environment that mirrors production. Deploy in controlled waves inside an approved maintenance window and verify the patch applied and the system still works with a back out plan ready. Those last steps are change management in action. Vendors release fixes on schedules you can plan around. Microsoft ships monthly security updates on the second Tuesday of every month nicknamed Patch Tuesday. Oracle issues quarterly updates. Vendors release out of band meaning emergency patches when a flaw is under active attack. To decide what goes first, combine the CVSS score for how bad, whether attackers are already exploiting the flaw, whether the system is internet facing, and how much it matters to the business.

Real teams also lean on EPSS scores and the government's known exploited catalog, though neither is named in the objectives. And don't forget third-party apps, browsers, firmware, and edge devices like VPN gateways, which attackers love because they get patched last. Sometimes you can't patch. Windows 10 is the live example. Microsoft ended its support on October 14th, 2025. Your options are to upgrade to Windows 11, buy paid extended security updates as a bridge, or isolate the machines. Whenever you can't patch, you use a compensating control. Segment the system, restrict who can reach it, switch off the vulnerable feature, or put a rule in front of it that blocks the known attack.

## 05:20 — Segmentation and access controls ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=320s))

Now let's talk about segmentation, isolation, and access controls. Segmentation means dividing your network into separate zones, so a problem in one can't freely spread to the others. It can be logical using software boundaries like VLANs or physical using separate hardware. Isolation is segmentation taken to the extreme like yanking an infected laptop off the network. Access controls limit who can do what once they're inside. Through permissions, access control lists, role assignments, and multi-factor authentication. The guiding idea is least privilege, giving each person exactly the access they need and nothing more. Remember this. Segmentation contains an attacker's movement, and access controls limit their reach. Next, sandboxing. Sandboxing means running a program or opening a file inside a walled-off environment, so even malicious code can't touch the real system.

Your browser sandboxes every tab. Email gateways can open suspicious attachments in a throwaway virtual machine and watch what happens before delivering them. Sandboxes aren't perfect, so treat one as a single layer.

## 06:34 — Deception: honeypots and tarpits ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=394s))

Now, deception and disruption technology. Most defenses try to keep attackers out. Deception invites them in to a place where every move triggers an alarm. Nobody legitimate has a reason to touch a decoy, so any contact is suspicious. A honeypot is a decoy system built only to be attacked and watched, the police bait car left unlocked with the keys inside. A honeynet is a whole decoy network of them, a fake neighborhood of bait cars. A honeyfile is a decoy file with a tempting name, like a spreadsheet called passwords, set to alert when opened. A honeytoken is a fake piece of data planted among the real stuff, like a made-up customer record or an unused access key.

If it ever shows up in use, something stole it. And a canary account is a decoy user account with no real purpose, so any login attempt is an instant alert. Disruption technology wastes the attacker's time instead. A tarpit answers connections painfully slowly, and a sinkhole redirects malicious traffic into a dead end. A warning. Deception tools are mostly detective controls. They don't stop an attack, they reveal one early. If a question asks which control alerts you the instant an intruder starts snooping with almost no false alarms, think honey token, honey file, or canary account. Monitoring and alerting come next. Monitoring means continuously collecting and watching logs and activity. Alerting means notifying someone when something looks wrong, like repeated failed logins.

Too many alerts leads to alert fatigue, so alerts need tuning. And monitoring is a detective control, so pair it with preventive ones. The monitoring lesson later in the course goes deep.

## 08:25 — Endpoint protection: AV, EDR, XDR ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=505s))

Now let's move on to endpoint and device protection. An endpoint is any device that connects to your network and does work. Endpoints are where users click things and where many attacks land first. Start with antivirus, EDR, and XDR. And XDR. Antivirus compares files against signatures, the fingerprints of known malware. It asks only, "Is this on my list of known bad things?" EDR stands for endpoint detection and response. It lives on each endpoint, watches behavior, and can react automatically, for example by isolating a machine that starts acting infected. It asks, "Is this program behaving like malware right now?" That helps against brand new threats and fileless attacks. XDR, extended detection and response, stretches that watching across endpoints, network, cloud, and email, and correlates the signals.

EDR is a sharp guard on one building. XDR is the command center pooling the guard, the parking lot cameras, and the front gate, and noticing the same suspicious person in all of them. The exam loves to swap these.

## 09:38 — Application control and allow lists ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=578s))

Application control is next and it's a favorite exam distinction. An allow list means only explicitly approved programs may run and everything else is denied by default. That's default deny. A block list means everything runs except what you flagged as bad. That's default allow. An allow list is a bouncer with a printed guest list. If you're not on it, you're out no matter how friendly you seem. A block list is a bouncer who's memorized photos of known troublemakers and lets everyone else in. The guest list is far safer because the bouncer doesn't need to recognize every troublemaker on Earth. Here's a quick tip. When a question asks which approach better stops unknown or zero-day malware, the answer is the allow list.

A host-based firewall runs on the device itself giving that machine its own gatekeeper. Host-based intrusion detection watches a single host and raises an alert, a detective control. Host-based intrusion prevention watches the same way but can block, a preventive control. The one-letter difference, D for detect and P for prevent, mirrors the network versions in the next lesson. Mobile device management or MDM lets an organization enforce security rules on phones and tablets from one console. It can require a passcode and encryption and remotely lock or wipe a lost device. It can block risky apps and side-loading, keep work data in a separate managed container, and geofence features by location. And it can cut off devices that are jailbroken or out of date.

Now content filtering and data loss prevention. A content filter blocks or allows traffic based on what it contains or where it's going like malicious sites or risky file types. It usually runs through a proxy or gateway that checks each request or through an agent on the endpoint that keeps working when a laptop leaves the office. Data loss prevention, or DLP, works from the other direction, stopping sensitive data from walking out, like a spreadsheet of card numbers attached to a personal email. Agent-based means software on each endpoint. It sees USB, printing, and the clipboard, even off the network, but must be installed everywhere. A centralized proxy funnels traffic through one gateway or cloud service that inspects it.

It's one place to manage, but can't see what never passes through it. Now, application security. Many attacks come down to how software was written. Input validation means

## 12:16 — Input validation and cookies ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=736s))

checking everything a user sends against what's allowed before using it, ideally with an allow list of expected formats. Do it on the server because checks in the browser are easy to skip. It's the common cure for injection, paired with parameterized queries, which keep input strictly as data. It also helps against buffer overflows and directory traversal. Secure cookies protect the files that keep you logged in. The secure flag means the cookie only travels over encrypted HTTPs. The HTTP only flag hides it from page scripts, so cross-site scripting can't steal it. And same-site limits when a browser sends it with requests from other sites, which blunts cross-site request forgery. Two more forgery defenses.

An anti-forgery token is a secret value the server puts in each form and checks on submission, so a malicious page that can't see it can't forge a request. And against server-side request forgery, the server keeps a strict allow list of destinations it may contact and refuses everything else, especially internal addresses.

## 13:24 — Code analysis, signing, secrets ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=804s))

Static code analysis examines source code without running it, scanning for flaws like injection patterns and hard-coded secrets. Its sibling, dynamic analysis, tests the running application like an attacker would. Static tools throw false positives, so humans review the results. Code signing attaches a digital signature to software, so you can verify who published it and that nobody has altered it. It's the tamper-evident seal on a medicine bottle, but a valid signature proves who sent it, not that it's safe. The SolarWinds updates were properly signed because attackers were inside the build system. A repository is where source code lives, and it's a juicy target, so protect it with access controls, multi-factor authentication, and protected branches.

Secret scanning automatically searches code and its history for things that look like passwords, keys, and tokens, and can block a risky submission before it lands. Here's a quick tip. A developer accidentally commits a client access key to a public repository. Revoke and rotate it immediately, then clean up and add scanning. Rotation comes first because bots find leaked keys within minutes. Now, email security. This is a big one.

## 14:42 — Email security: SPF, DKIM, DMARC ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=882s))

Email was built when everyone trusted everyone. By default, anyone can type any name in the from line, which is how attackers impersonate your boss. Four standards fix that. Each answers a different question. SPF, sender policy framework, answers, is this server allowed to send mail for that domain? The domain owner publishes a list in DNS, the internet's phone directory, of the servers allowed to send that email. The receiver checks the list, and anyone not on it counts as failing. What happens to a failure is up to the receiver and DMARC. It's the approved carrier list of the loading dock. If the truck isn't on it, it's suspect. DKIM, domain keys identified mail answers, is this message really from that domain and was it altered on the way?

The sending server signs each message with a private key and the matching public key sits in the domain's DNS, so the receiver can check. It's a wax seal pressed with a signet ring only the real sender owns. DMARC, which stands for domain-based message authentication, reporting and conformance, answers, what do we do when those checks fail and who gets told? It demands alignment, meaning the domain that passed must match the domain the user sees in the from line. And the owner publishes a policy. None means monitor only. Quarantine sends failures to spam. Reject refuses them outright. DMARC also sends the owner reports showing everyone sending mail in their name. Organizations start at none, clean up, then tighten to reject.

It's the company's instruction to the mail room. If the truck isn't on the list or the seal is broken, throw it away and send me a daily report. BIMI, brand indicators for message identification, answers, can the recipient see at a glance that this really is the brand? When a domain enforces DMARC and has a verified logo certificate, supporting mailboxes can show the company's logo beside the message. It's real value is that it rewards domains for doing DMARC properly.

## 16:56 — The spoofed CEO email walkthrough ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=1016s))

Let's walk through the spoofed CEO email. Your company is acmefoods.com and an attacker sends your accounts team an email showing the CEO's address. Attempt one is a straightforward forgery. The attacker sends from their own server and fakes acmefoods.com everywhere. SPF fails because their server isn't on the approved list. DKIM fails because they have no private key. DMARC sees both because they have no private key. DMARC sees both fail with a reject policy and the email is refused before it reaches anyone. Attempt two is the alignment trick. The attacker sets the hidden sender address to their own domain where they control SPF so it passes. They only display Dana's address in the from line.

SPF passed but for the wrong domain. DMARC's alignment check catches it. That's exactly why DMARC exists. Attempt three is a look-alike domain. The attacker registers acmef00ds.com, sets up perfect SPF, DKIM, and DMARC for it, and sends from it. Every check passes because they're correctly authenticating their own domain. Email authentication can't stop this one. That's where training, external mail banners, and phone confirmation of payment requests come in. So remember, SPF checks the sending server, DKIM checks the message signature, DMARC sets policy and reporting on top, BIMI shows the logo. If a question asks which one tells receivers to reject failed mail, it's DMARC. A warning. These prove a message came from the domain it claims, not that the sender is trustworthy.

Big providers now expect all three. Google and Yahoo began requiring them from bulk senders in 2024 and Microsoft followed in 2025. Now operating system security.

## 18:55 — Operating system security ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=1135s))

Group policy is how Windows administrators centrally control computers and users in an active directory domain. An administrator builds a bundle of settings called a group policy object and links it to part of the organization. Every computer there picks it up automatically and rechecks roughly every 90 minutes. It can enforce password rules, set screen lock timers, block USB storage, and control which apps run. It's the building's master rulebook applied to every office at once. SELinux, Security-Enhanced Linux, is a security layer built into the Linux kernel, originally developed by the National Security Agency. It uses mandatory access control. Every file, process, and port gets a label, and a central policy decides which labels may interact, even for administrators.

A hacked web server can only do what the web server's policy allows. It runs in enforcing mode, which blocks violations, permissive mode, which only logs them, or disabled. Don't mistake permissive mode for protection.

## 20:06 — Choosing the best mitigation ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=1206s))

Finally, choosing the best mitigation. Given a threat, which mitigation is the best fit? Not which one would technically help, because several usually would. The best one, ask what the scenario needs. Stop it from happening, that's preventive, like hardening, patching, allow lists, and access controls. Know it happened, that's detective, like logging and honey tokens. Fix it afterward, that's corrective, like restoring from backup. And if the ideal control isn't feasible, reach for a compensating control, the spare tire that gets you home. Try a quick example. A legacy application requires an outdated operating system that can no longer be patched, and it can't be replaced for 18 months. The word can't is your signal.

The ideal preventive fix is off the table, so you compensate. Segment or isolate that system on its own restricted zone. The most important habit is that no single mitigation is enough. Hardening shrinks the surface. Patching closes known holes. Segmentation contains what gets through. Endpoint tools catch what lands. Access controls limit the damage. That's defense in depth, the layered onion made concrete. Here are a few more scenarios. First, employees keep running unauthorized software they download. The best fit is an allow list. Second, a critical server can't go offline for patching, but a severe flaw is being actively exploited. What do you do first? Use a compensating control that cuts exposure now, like restricting network access to it, until the maintenance window arrives.

Third, executives keep getting emails that appear to come from your own domain, and you want receiving service to reject them automatically. That's DMARC with a reject policy. Read the qualifier, best or first, decide what the situation needs, then match a control by its type. That single habit answers a huge share of mitigation questions.

## 22:12 — Review and key takeaways ([↗](https://www.youtube.com/watch?v=pIuq5o8htcw&t=1332s))

Let's review what we covered in this lesson. Mitigations are security controls chosen to fit a threat. Hardening shrinks the attack surface, standardized through baselines and configuration management. Patch management means identify, prioritize by severity, exposure, and active exploitation. Test, deploy in a maintenance window, and verify. When you can't patch, use compensating controls like isolation, segmentation, access controls, sandboxing, and deception tools contain damage, limit reach, and sound the alarm early. Antivirus matches signatures, EDR watches behavior on the device, and XDR correlates across layers. Allow lists are default deny and the stronger choice. Mobile device management controls phones and content filters and data loss prevention control what comes in and leaks out. Application security means input validation, secure cookies, anti-forgery tokens, and allow lists, static code analysis, code signing, and secret scanning.

SPF says who may send, DKIM says the message is signed and untampered, DMARC sets policy and reporting, and BIMI shows the logo. Group Policy and SE Linux enforce settings on Windows and Linux. And no single mitigation is enough. Layer them into defense in depth. Now, here's a quick check to lock it in. First question. A system can't be patched because a legacy application needs its outdated operating system, and it can't be replaced for over a year. What type of control should you reach for, and what's the best practical move? You reach for a compensating control because the ideal preventive fix, patching, isn't feasible. The best practical move is to segment or isolate that system on its own restricted zone so the weakness can't be reached or spread.

Second question. An attacker sends an email showing your CEO's address in the from line, but from their own server. Which email standard tells receiving servers to reject it, and why do SPF and DKIM alone fall short? DMARC. SPF and DKIM check whether the server is allowed and the message is signed, but they don't tell receivers what to do when checks fail. DMARC adds the policy, the alignment requirement, and the reporting. Third question. Which is the stronger control against unknown or zero-day malware, an allow list or a block list and why. The allow list is default deny, so only approved programs run. A block list is default allow, so it only stops threats it already knows about.
