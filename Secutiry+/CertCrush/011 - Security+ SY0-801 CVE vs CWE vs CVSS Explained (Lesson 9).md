## 00:00 — Threat, vulnerability and exposure ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=0s))

An attacker with the best tools in the world still needs a way in. That way in is a vulnerability, a weakness in your code, your configuration, or something you inherited from a supplier you've never even met. This lesson closes out the knowing your enemy series. Earlier lessons covered who attacks and how. Now you'll see what they exploit and the attacks that use those weaknesses. Lock in one distinction right away. A vulnerability is the flaw. A threat is who might use it. Risk is the two combined. The exam tests that constantly. In this lesson, you'll learn five things. First, flaws in applications and code like race conditions, malicious updates, hard-coded secrets, and unsafe error handling.

Second, weaknesses in systems and identities from unsupported software and open ports to stale credentials, rogue devices, and public storage. Third, the application attacks including injection, buffer overflows, replay, forgery, and directory traversal. Fourth, credential attacks from password spraying to MFA bypass. And fifth, how CVE, CWE, ONVD, and CVSS help you name and score the flood. And how exposure and impact turn scores into priorities.

## 01:21 — Application and code flaws ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=81s))

Let's start with flaws in applications and code. Software is written by humans and humans make mistakes. Attackers hunt for those mistakes. First, race conditions. A race condition is a timing flaw. The outcome depends on the order of events that aren't properly controlled and an attacker slips in during the gap. The classic form is time of check and time of use, written TOCTOU. The program checks something, like whether you have permission to open a file. Then it acts on that answer. If an attacker changes things in between, the check no longer means anything. Think of a bouncer who checks your ID, then turns to stamp your hand. In that split second, you swap in a fake.

The check passed, but the thing being used isn't the thing that was checked. The usual fix is locking, so the check and the use happen as one step with no gap. Next, malicious updates. This is tampered software that arrives through the one channel everybody trusts, the vendor's own update process. The best-known case is the 2020 SolarWinds compromise. Attackers broke into a product's build system and slipped a backdoor into properly signed updates. Reportedly, around 18,000 organizations installed it. In 2024, the XZ Utils backdoor showed a slower version. An attacker spent about 2 years earning trust as a maintainer of a widely used library, then planted a backdoor. An engineer caught it when logins ran half a second slow before it reached most stable systems.

Don't confuse a malicious update with a bad one. The 2024 CrowdStrike outage was a faulty update, a mistake, not an attack. Attacker tampering means malicious update. A plain bug is a quality control and change management problem.

## 03:17 — Hardcoded secrets and insecure code ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=197s))

Now, hard-coded secrets. That's a password, key, or token typed straight in the source code or a configuration file. It's like taping the safe's combination to the safe. Anyone who can read the code can read the secret. In Uber's 2022 breach, the attacker found administrator credentials sitting in plain text scripts and used them to reach far more systems. The fix is to keep secrets out of code and fetch them at runtime from a secrets manager. The next lesson covers secret scanning, which catches them before they ship. And unsafe exception handling. An exception is what a program does when something goes wrong, and it can go wrong in four ways. It can leak details like file paths or software versions in an error page, which is free reconnaissance.

It can fail open, letting a request through when a security check breaks, like a vault door that swings open when the alarm computer crashes. It can swallow errors silently, or it can crash, turning a small bug into an availability problem. The safe pattern is to fail closed, show users a bland generic message, and log the details privately. Here's a quick tip. If an error message reveals database table names to a visitor, think unsafe exception handling.

## 04:34 — Weaknesses in systems ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=274s))

Now, let's move on to weaknesses in systems. Many of the worst holes are boring, and that's why they get missed. Four terms here sound alike. An unsupported product is one the vendor stopped patching. An unpatched system has a fix available that nobody applied. An obsolete system is old technology, often impossible to replace. And an unmanaged system is one nobody is tracking or monitoring. Unsupported software is a house whose locks are being sold on the black market, and the locksmith has retired. Windows 10 is the real example. Microsoft ends its support on October 14th, 2025. So, no more free security updates. Paid extended security updates are a bridge. Consumers can enroll through October 12th, 2027, and businesses can buy up to 3 years, but that's a stopgap while you move to Windows 11.

Obsolete systems, like a medical scanner or factory controller tied to a decades-old operating system, can't be patched or replaced without huge cost. The answer usually isn't patch it. It's isolated, restrict access, and plan its replacement. Unpatched systems are the most common problem. The vendor published the fix, attackers read the notes to learn exactly what's broken, and they race the delay. Unmanaged systems, like a forgotten test server, are outside your control. You can't protect what you don't know exists. Then ports and services. Every service listens on a numbered port, and each open port is a door with code behind it. A web server on port 443 is expected. A forgotten Telnet service on port 23, remote desktop on port 3389, or VNC, a screen sharing tool, on port 5900, exposed to the whole internet, is an invitation.

If a service isn't needed, turn it off. If it is, limit who can reach it. Operating system flaws, like kernel bugs, weak defaults, and over-privileged services, are especially dangerous because everything sits on top of them. But a word of warning. Default credentials, misconfigurations, and unpatched software cause far more real breaches than exotic zero days. When a scenario offers a flashy answer, and a boring one like apply the patch, the boring one is very often correct. Virtualization has its own weak spots. A virtual machine escape is when an attacker breaks out of one machine and reaches the hypervisor, the software managing them all. It's rare, but severe. Hypervisors are high-value targets, and ransomware crews have gone straight after them.

Virtual machine sprawl is forgotten. Unpatched machines piling up, and old snapshots can quietly restore old flaws and passwords. A zero-day is a vulnerability unknown to the vendor, with no patch yet. Defenders had zero days to prepare. Zero-days are dangerous, but relatively rare. Since you can't patch what has no patch, you lean on layered controls like segmentation, least privilege, and application control. Cryptographic vulnerabilities are next. If it's an IO describes strong encryption that still failed, look for the human or implementation error. Now, let's turn to identity, device, and exposure weaknesses. Stale credentials are accounts, passwords, keys, and tokens that should have been removed or changed but weren't.

A former employee's login that still works. If the key card of someone who left a year ago that still opens the front door. Unmanaged credentials are ones nobody owns like shared admin passwords in a spreadsheet and factory default logins. The defense is a disciplined identity life cycle. Remove access when people leave, review who has what, and rotate secrets. An identity provider approves who you are to many applications. It's the front desk that prints everyone's badge and every door trusts the badge. That makes it a giant target. In the 2023 Storm-0558 incident, attackers obtained a Microsoft signing key and forged tokens that opened email at about 25 organizations including government agencies.

Protect the identity provider like the crown jewels, with strong multi-factor authentication on every admin, tight control of signing keys, and close monitoring. A rogue device is unauthorized hardware on your network, like a stranger's laptop in a conference room jack, or a rogue wireless access point. Shadow IT

## 09:53 — Shadow IT, mobile and IoT ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=593s))

is hardware, software, or cloud services staff use without approval. It's usually well-meant, and it leaves company data somewhere nobody is patching or monitoring. Mobile devices live in pockets, get left in taxis, and join any coffee shop network. Watch for lost devices, side-loading, which means installing apps from outside the official store, jailbroken or rooted phones, outdated operating systems, and over-permissioned apps. Wireless and low-powered communications like Bluetooth, Zigbee, and NFC bring several problems. Encryption is weak or missing. Pairing is weak with default PIN codes. Tiny devices can't run strong encryption or accept updates. And relay attacks stretch a key fob's short range far beyond its limit. Misconfiguration is a setting left wrong, like an overly permissive firewall rule or debug mode left on.

## 10:49 — Misconfiguration and cloud exposure ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=649s))

Nothing was hacked. Someone set it up carelessly. It ranks second on the 2025 OWASP top 10 for web applications. It feeds two big exposures. Public repositories are code-sharing spaces anyone can read, and developers sometimes push keys, passwords, and internal server names. Git Guardian reported about 28.65 million new hardcoded secrets in public GitHub commits in 2025, up 34%. Here's a quick tip. If a secret ever touches a public repository, treat it as stolen. Deleting the file doesn't erase the history. rotate the secret. Public object storage is cloud file storage like Amazon S3 buckets set so anyone on the internet can read it. Nobody has to hack anything and automated tools hunt for open buckets all day.

In the cloud, the top cause of breaches isn't clever hacking. It's someone leaving the door open. For cloud questions, misconfiguration is your default suspect. Large language models or LLMs are a newer attack surface. They mix instructions and data in one stream so hidden instructions in a webpage can trick them and they're often wired to company data and tools. Prompt injection tops the OWASP list for these applications. The AI threats lesson covers the full set. ## 13:08 — Application attacks and defences ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=788s))

Now, let's cover the attacks themselves starting with application attacks. Injection tricks a program into running attacker supplied input as if it were a command. SQL injection targets the database behind a website. Command injection feeds commands to the operating system. Cross-site scripting or XSS injects a script into a page so visitors' browsers run it. Imagine a clerk who obeys any note. You write, "My name is Bob, and also empty the cash register." The clerk obeys. The fix is input validation plus parameterized queries that keep input strictly as data. A warning. SQL injection and XSS aren't a named list in the SY0-801 objectives anymore, but injection still is, and they remain the textbook examples.

A buffer overflow is when a program writes more data into memory than it can hold, spilling into neighboring memory, like pouring too much water into a cup. Attackers use the spill to plant their own instructions. The defenses are bounds checking, input validation, and memory-safe languages. A replay attack catches a valid message or session token and sends it again later. The attacker never needs the password, just a recording, like replaying someone saying, "Open sesame." Defenses make each message good for one use through one-time values, timestamps, short sessions, and encryption. Privilege escalation is gaining more access than you were given. Vertical escalation is a regular user becoming an administrator. Horizontal escalation is reaching another user's data at the same level, like changing an account number in a URL.

Least privilege and patching shrink the room an attacker has to climb. Forgery makes a request or credential look legitimate. CSRF tricks your logged-in browser into making a request you didn't intend. It abuses the trust a website has in your browser. SSRF tricks a server into making requests for the attacker, often to internal systems. In the 2019 Capital One breach, that kind of flaw let an attacker get a cloud server to hand over credentials, exposing about 100 million people's data. And token forgery fakes the proof of identity itself, like Storm-0558. To keep two similar ones straight, XSS abuses the trust a user has in a website, while CSRF abuses the trust a website has in your browser.

In CSRF, your browser is the puppet. In SSRF, the server is. Directory traversal tricks an application into reading files outside its folder. The attacker supplies {dot} {slash} repeated to climb out of the web folder into the system's files. It's like writing on a hotel request slip, go up three floors and bring me the manager's files. The defenses are validating file paths, never building paths straight from user input, and minimal permissions.

## 16:19 — Credential attacks and MFA bypass ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=979s))

Now, let's look at credential attacks. A brute force attack tries many guesses against one account. A dictionary attack tries likely passwords first. Offline attacks work on a stolen file of hashes with no lockout to slow them. Password spraying flips it. A few very common passwords tried against many accounts. Each account sees only a failure or two, so lockouts never trigger. Brute force is one door and 10,000 keys. Spraying is one key on 10,000 doors. In the 2024 breach Microsoft disclosed, the group Midnight Lizard sprayed passwords slowly at a legacy test account with no multi-factor authentication, then reached corporate email. Credential stuffing is a cousin, replaying username and password pairs leaked from other breaches.

Here's a quick tip. One account with thousands of failures is brute force. Many accounts with a failure or two each is spraying. User enumeration is finding which usernames are valid. The leak is usually an error message. If a login says no such user for a bad name, but wrong password for a good one, it has confirmed which accounts exist. The fix is the same answer every time, invalid username or password. Replay applies to credentials, too. In pass-the-hash, the attacker steals the password hash and uses the hash itself to log in. A stolen session cookie can take over a session with no password at all. And MFA bypass. Multi-factor authentication blocks most credential attacks, so attackers invented ways around it.

Fatigue floods the victim's phone with approval prompts until they tap approve to make it stop. In the 2022 Uber breach, the attacker also messaged the contractor posing as IT support. Adversary-in-the-middle phishing relays a fake login page to the real one and steals the session token. SIM swapping moves your number to the attacker, so text codes reach them. Help desk social engineering talks support into resetting MFA, and legacy protocols and weak fallbacks give attackers an easier door. The defenses are number matching, phishing-resistant MFA like passkeys and hardware keys, blocking legacy authentication, and strict identity checks at the help desk. Text codes and plain push approvals are weakest. Passkeys and hardware keys are the strongest answer.

## 18:53 — CVE, CWE, NVD and CVSS ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=1133s))

In 2025, roughly 48,000 new vulnerabilities were published, about 130 a day. You need a shared way to name and rank them. A CVE, common vulnerabilities and exposures, is a unique ID for one specific publicly known vulnerability, like a case number. A CWE, common weakness enumeration, names a type of flaw instead. The CVE is the case number for one burglary. The CVE is the case number for one burglary. The CWE is the category, burglary through an intruder to an author, and the NVD, the national vulnerability database, adds detail to CVE entries, like severity scores and affected products. A CVSS, the common vulnerability scoring system, rates severity from 0 to 10. Version 3.1 and the newer 4.0, published in November 2023, both circulate.

The bands are the same. 3.1 had base, temporal, and environmental groups. 4.0 renames temporal to threat and added supplemental. 9 to 10 is critical. 7 to 8.9 is high. 4 to 6.9 is medium. 0.1 to 3.9 is low. The base score asks how reachable the flaw is, how hard to exploit, whether it needs an account or a click, and how badly confidentiality, integrity, or availability could be hurt. In 4.0, base is the flaw's built-in severity. Threat covers whether exploits exist. Environmental covers how important the system is to you, and supplemental adds context without changing the score. Most published scores are base only, so they say how bad in theory, not how bad for you.

## 20:50 — Prioritising with real evidence ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=1250s))

So, prioritization adds evidence. Is the system exposed to the internet? Does it hold sensitive data? Are attackers already using the flaw? A critical flaw on an isolated server can be less urgent than a medium flaw on a public server holding customer data. One extra, not named in the objectives, real teams also use EPSS, a free score giving the probability that a flaw will be exploited in the next 30 days, and the Cybersecurity and Infrastructure Security Entities Known Exploited Vulnerabilities Catalog, a list of flaws with confirmed attacks. Keep CVE, CWE, VD, and CVSS as your tested set. The pattern is severity plus likelihood plus exposure plus impact. When a scenario asks what to fix first, look for the high score on an exposed, actively exploited system.

A high CVSS alone shouldn't drive your answer. The vulnerability management lesson puts this into practice.

## 21:52 — Review and key takeaways ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=1312s))

Let's review what we covered in this lesson. Application and code weaknesses include race conditions, malicious updates, hard-coded secrets, and unsafe exception handling. System weaknesses include unsupported, unpatched, obsolete, and unmanaged systems, risky ports, operating system flaws, virtualization issues, zero days, and cryptographic mistakes. Stale credentials, identity providers, rogue devices, shadow IT, mobile and wireless devices, misconfiguration, public repositories and storage, and LLM applications widen your attack surface. Misconfiguration is the default suspect for exposed cloud data. The application attacks are injection, which input validation stops, buffer overflow, replay, privilege escalation, forgery, and directory traversal. The credential attacks are brute force, password spraying, user enumeration, replay, and MFA bypass. And CVE names a vulnerability, CWE names a weakness type, and CVSS scores severity.

While exposure, impact, and evidence of active exploitation sharpen your priorities. Now, here are a few quick checks.

## 23:11 — Quick self-check questions ([↗](https://www.youtube.com/watch?v=npIynPoRltA&t=1391s))

Here's the first one. A login page says that username does not exist for some names and wrong password for others. What attack does this enable and what's the fix? User enumeration. The different messages reveal which accounts are real. The fix is the same generic answer with the same timing every time, plus rate limiting. Here's the second check. You see one or two failed logins on thousands of accounts all trying the same common password. What is it and why didn't lockout catch it? Password spraying. Each account sees only a failure or two, so the lockout threshold never triggers. Multi-factor authentication and monitoring across accounts are the best defenses. And here's the third.

A server runs an operating system the vendor no longer patches and it can't be replaced for a year. What's the best practical move? Isolate it. It's unsupported and can't be patched, so you compensate with segmentation, strict access limits, and extra monitoring while you plan its replacement. That wraps up knowing your enemy.
