First, let's talk frameworks. You probably know MITER AT and CK. It maps how hackers move through a network from initial access to Xfiltration. But if you try to map an AI attack to that chart, it fails. Why? Because stealing a model is different than stealing a password. Enter MITER atlas. This stands for adversarial threat landscape for artificial intelligence systems. It looks like the standard AT and CK matrix, but look closer at the tactics. You still have reconnaissance, but instead of persistence, you have ML model access. This is a tactic specifically for gaining unauthorized access to the model or its parameters. You also have ML attack staging. This covers steps like poisoning the training data before the model is even trained.

For the exam, remember this ATLAS is based on realworld case studies. Every technique in this matrix comes from a documented attack against a real AI system. If you need to analyze an attack chain against an LLM, you use Atlas, not attack. Now, let's broaden the scope. Besides Atlas, CompTIA wants you to know the MIT AI risk repository. Think of Atlas as the hacker's playbook. The MIT repository is the risk manager database. It catalogs every risk, including non-technical ones like corporate espionage or human safety risks. Also, pay attention to the CVE AI working group. We are finally seeing official CVEes specifically for AI models. You need to check these feeds just like you check for Windows updates.

Next up is the OWASP LLM top 10. This isn't just a list, it's a hierarchy of risk. Number one is prompt injection. But why does this happen? It happens because LLMs cannot distinguish between instructions, what you told it to do, and data, what the user typed. If a user types ignore previous instructions, the model thinks that is a new instruction. That fundamental flaw is why LLM01 exists. Then look at LLM02, insecure output handling. This is the downstream effect. If your AI writes a SQL query based on a prompt and your app runs that query blindly, you have just given the AI remote code execution privileges on your database. Now let's talk about supply chain risk.

In traditional software, you worry about malicious libraries. In AI, we worry about hugging face and model serialization. Here is the deep technical detail you need. Most AI models are saved as Python pickle files. The pickle format isn't just data. It's a protocol that allows valid Python code to be saved and restored. This means I can hide a malicious script inside the model file. When you load that model to run inference, my script executes on your server. This is why you never trust a model from an unverified source. So, how do we defend against this? We use threat modeling. We apply methodologies like street. In an AI context, tampering isn't just changing a file.

It's poisoning the training data so the model learns the wrong things. Information disclosure isn't just a data breach. It's model inversion where an attacker queries the AI to reverse engineer the private data it was trained on. We are going to deep dive into every single one of these attacks in the next few videos.
