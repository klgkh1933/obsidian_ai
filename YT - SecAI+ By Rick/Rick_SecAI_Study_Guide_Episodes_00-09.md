## 1. Essential mental model and exam map

### 1.1 The guiding principle

**Most AI-security failures cannot be solved by asking the model to behave better. Security is built into the architecture around the model.** That architecture includes authenticated identities, data access boundaries, trusted sources, model and dependency integrity, an API gateway, tool permission controls, monitoring, evaluation and governance.

Rick's recurring message is **AI security architecture + framework fluency**. You should be able to:

1. Identify the **asset** at risk: data, model weights, decision correctness, service availability, money, or a connected system.
2. Identify the **lifecycle stage**: sourcing, training, model artifact, build pipeline, inference, retrieval, or tool execution.
3. Name the **threat mechanism**, not just its label.
4. Describe the **CIA impact**: confidentiality, integrity, or availability.
5. Choose a **preventive control**, a way to **detect failures**, and a response.
6. Relate the decision to a suitable **framework**, and identify evidence that the control works.

**One-line rule:** *Locate the stage → understand the trust boundary → identify the attack → apply the control.*

### 1.2 Attacks **on** AI versus attacks **using** AI

| Attacks **on AI** | Attacks **using AI** |
|---|---|
| AI system is the target: poison it, manipulate prompts, evade it, extract weights, or exhaust its API. | AI is the attacker's tool: generate convincing phishing, deepfakes, malware or automated reconnaissance. |
| Main focus of SecAI+ domain 2. | Mainly discussed in domain 3, which also covers how defenders use AI. |
| Ask: **How can we protect this AI system?** | Ask: **How does AI change offensive or defensive work?** |

## 2. Machine-learning foundations for defenders

### 2.1 Traditional programming versus ML

**Traditional rule-based software** generally executes logic explicitly written by programmers. **Machine learning (ML)** estimates patterns and behavior from examples rather than receiving a complete list of rules.

| Traditional software | ML-based software |
|---|---|
| Behavior is primarily described in code and configuration. | Behavior depends on architecture, **training data**, and learned **parameters/weights**. |
| Code inspection can help explain program logic. | Code inspection is necessary but cannot fully establish what the model learned. |
| Many operations can be deterministic. | Generative responses may vary with sampling, prompt and context. |
| Threats include normal application vulnerabilities. | All traditional vulnerabilities **plus** data poisoning, adversarial examples, extraction, privacy inference, etc. |

**Technical nuance:** Not all conventional software is deterministic, and not all ML inference is random. A model can generate reproducible outputs under controlled settings. The deeper difference is **learned behavior and incomplete explainability**, not unavoidable randomness.

### 2.2 Two phases: training and inference

**Training**: The model processes examples and adjusts numerical parameters to reduce its error. Its output is a trained model or updated weights.

**Inference**: A trained model receives an input and produces a prediction, score, classification, or generated text. It is the live use phase.

| Training time | Inference time |
|---|---|
| Sources, labels, transformations, training code, tuning jobs. | User requests, documents, context, retrieved sources, endpoint queries. |
| Attacks change what the model **learns**. | Attacks exploit or manipulate how the trained model is **used**. |
| Examples: poisoned labels, tampered fine-tuning, backdoors. | Examples: evasion, prompt injection, extraction, inversion. |
| Controls: provenance, data validation, restricted training environment, promotion gates. | Controls: auth, rate limits, policy enforcement, output validation, monitoring. |

**Fine-tuning (background)**: Further training a pre-trained model on a smaller, task-specific dataset. Trustworthy base weights do **not** guarantee trustworthy fine-tuned behavior.

**Epoch (background)**: One complete pass over the training set during training.

### 2.3 Learning types and security implications

| Type                           | Meaning                                                                  | Security concern                                                                    |
| ------------------------------ | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| **Supervised learning**        | Learns from examples with target labels, such as spam/not spam.          | Labels and examples may be corrupted.                                               |
| **Unsupervised learning**      | Finds structure in unlabeled data, such as clusters or unusual behavior. | The notion of “normal” is learned from the dataset; poisoned baselines can mislead. |
| **Reinforcement learning**     | Learns choices/actions from rewards or feedback.                         | A poorly designed reward can optimize unwanted outcomes.                            |
| **Neural network**             | Layered computations with numerical weights.                             | Weights encode learned behavior and are valuable intellectual property.             |
| **Transformer**                | Neural network architecture using attention across token sequences.      | Common basis for LLMs; context can include mixed-trust material.                    |
| **Large Language Model (LLM)** | Usually a transformer-based model predicting/generating token sequences. | Can output plausible errors and follow malicious instructions in context.           |

**Generative AI (background)** creates content such as text, images or code. **Predictive AI** produces a class, probability, score or forecast. Both require security, although their risks differ.

### 2.4 Vocabulary you must understand

- **Model weights / parameters**: Learned numerical values that determine model behavior.
- **Model architecture**: Structure of the computation and layers.
- **Token**: Unit of text or another representation processed by a model; not necessarily one word.
- **Context window**: Information available to the model for a response, including system instructions, chat history, retrieved material and tool outputs.
- **Decision boundary**: Mathematical region separating possible classification outcomes.
- **Gradient**: Direction and magnitude of a change in a mathematical function, used in learning and sometimes adversarial attacks.
- **Inference API**: A service endpoint allowing callers to submit an input and receive the model's output.
- **Model artifact**: Stored weights and related files, configuration and metadata needed to load or deploy a model.

### 2.5 Why this introduces new security challenges

1. **Non-determinism / variability**: A successful test of a generative system is not a guarantee of all future behavior. Test adversarial variations and different contexts.
2. **Data dependence**: Corrupt or unauthorized training/tuning data can affect model behavior invisibly until used.
3. **Opacity**: Weights are not generally a human-readable explanation of specific decisions. Evidence must come from documentation, evaluation, monitoring and controls.

Rick's shorthand is **model = data + code + weights**. For security, broaden it to **data + training/build pipeline + model artifact + application + access controls + retrieval + tools + operations**.

> [!tip] Retrieval question
> A model was trained last month on altered fraud labels; another correctly trained model is fooled today by a specially crafted transaction. Which failure is at **training time**, and which is **inference-time evasion**? Why do their controls differ?

## 3. AI attack surface and CIA triad

**Attack surface (background)**: All the places an attacker can reach, influence, abuse or extract value from a system.

### 3.1 The six-stage AI attack-surface map

| Stage | Exposed material | Representative attack | First-line protection |
|---|---|---|---|
| **1. Data** | Training examples, labels, documents | Poison datasets, substitute source data | Approve sources, provenance, quality and integrity checks |
| **2. Training/tuning** | Learning jobs, configurations, resulting weights | Backdoor / Trojan model, compromised fine-tune | Restrict access, isolate jobs, audit and evaluate |
| **3. Model and weights** | Artifact files, model weights | Steal model; tamper with artifact | Protect storage, verify hash/signature, limit access |
| **4. MLOps pipeline** | Registry, builds, packages, dependencies | Compromised package or model delivery | Review, scan, pin and sign dependencies/artifacts |
| **5. Inference endpoint** | Queries and model outputs | Evasion, extraction, inversion, membership inference, direct injection | Auth, quotas, output minimization, monitoring |
| **6. Applications / RAG / agents** | Retrieved text, tool calls, output consumers | Indirect injection, insecure output handling, excessive agency | Access checks, independent tool authorization, output validation |

**Locate a threat on this map before naming a control.** Traditional network and software protections still matter; AI adds *new* trust dependencies, not a replacement for conventional cybersecurity.

### 3.2 CIA applied to AI

**CIA triad (background)** means **Confidentiality**, **Integrity**, **Availability**.

| Property | AI meaning | Example |
|---|---|---|
| **Confidentiality** | Protect training data, prompts, user input, outputs, weights and secrets from unauthorized disclosure. | Membership inference, model inversion, stolen model, data exfiltration. |
| **Integrity** | Preserve intended model behavior, input evidence and accuracy of decisions. | Poisoning, adversarial evasion, prompt injection, compromised outputs. |
| **Availability** | Preserve service use and manage resource/cost limits. | Denial of service and **denial of wallet** (deliberate inference-cost inflation). |

A single attack can affect several properties. An indirect injection that changes an answer **and** sends a private document externally impacts both **integrity** and **confidentiality**.

**Denial of wallet**: Abusing a costly AI endpoint to generate bills rather than, or in addition to, making the service unavailable.

### 3.3 What is a trust boundary?

**Trust boundary (background)**: The point where information or authority crosses from one security domain, identity or privilege level to another.

Important boundaries include third-party data → retrieval index; user input → model; retrieved text → model; model-generated output → browser/database/shell; model request → privileged tool; downloaded model → production runtime.

**Ask at every boundary:** Who controls the input? What could it influence? Where is authorization independently enforced? What is logged, and what is the fallback when a control fails?

## 4. Four framework families and OWASP version changes

Rick's phrase **“four maps, one territory”** means these frameworks are complementary, not competitors.

| Framework | Category | Question it answers | Typical use |
|---|---|---|---|
| **OWASP LLM Top 10** | Application-risk taxonomy | **What can go wrong in LLM applications?** | Security design reviews, threat categories, prioritization |
| **MITRE ATLAS** | Adversary tactics and techniques | **How does an attacker do it?** | Red teaming, threat intelligence, detection engineering |
| **NIST AI Risk Management Framework** | Continuous risk process | **How do we understand, measure and handle AI risks?** | Program-level risk ownership and decisions |
| **ISO/IEC 42001** | AI management-system standard | **How do we manage AI through auditable organizational processes?** | Policies, roles, evidence, audits and continual improvement |

### 4.1 OWASP Top 10 for LLM Applications — **2025 edition taught by Rick**

| 2025 ID | Risk | Meaning |
|---|---|---|
| **LLM01** | Prompt Injection | Crafted instructions redirect model behavior. |
| **LLM02** | Sensitive Information Disclosure | Model or app reveals private information, secrets or proprietary data. |
| **LLM03** | Supply Chain | Models, data, libraries or other external dependencies are unsafe. |
| **LLM04** | Data and Model Poisoning | Learning inputs, model artifacts or knowledge sources are corrupted. |
| **LLM05** | Improper Output Handling | Untrusted model output is passed dangerously to other components. |
| **LLM06** | Excessive Agency | Model/agent has unnecessary permissions, tools or autonomy. |
| **LLM07** | System Prompt Leakage | Internal prompt instructions may be disclosed and exploited. |
| **LLM08** | Vector and Embedding Weaknesses | Retrieval and similarity-search pipeline can be manipulated or leak information. |
| **LLM09** | Misinformation | Fluent but incorrect model output may cause damage. |
| **LLM10** | Unbounded Consumption | Unrestricted queries increase cost or exhaust resources. |

**[2026 update — important]** OWASP issued a **2026 revision on August 4, 2026**, which **changes several numbers and categories**. Do not memorize unqualified LLM03 or LLM05 without a release year.

| 2026 ID | 2026 risk |
|---|---|
| LLM01 | Prompt Injection |
| LLM02 | Sensitive Information Disclosure |
| LLM03 | **Excessive Agency** |
| LLM04 | **Supply Chain** |
| LLM05 | **Data and Model Poisoning** |
| LLM06 | **Unbounded Consumption** |
| LLM07 | **Misinformation** |
| LLM08 | **Hidden Context Exposure** |
| LLM09 | **Vector and Embedding Weaknesses** |
| LLM10 | **Improper Output Handling** |

**Examples of renumbering:** Rick's **2025 LLM05 = Improper Output Handling**, but **2026 LLM05 = Data and Model Poisoning**. Rick's **2025 LLM06 = Excessive Agency**, but **2026 LLM03 = Excessive Agency**. The newer **Hidden Context Exposure** category has related but not identical scope to the older **System Prompt Leakage** risk.

### 4.2 MITRE ATLAS

**MITRE ATLAS** stands for **Adversarial Threat Landscape for Artificial-Intelligence Systems**. It documents adversary behavior against AI systems, similar in spirit to MITRE ATT&CK for enterprise IT.

**Tactic:** What the adversary aims to achieve. **Technique:** Method used to achieve it. Identifiers begin with **AML.T**.

| ID | Technique / relevance |
|---|---|
| **AML.T0051** | LLM Prompt Injection |
| **AML.T0020** | Poison Training Data |
| **AML.T0024** | Exfiltration via AI/ML Inference API |
| **AML.T0010** | AI/ML Supply Chain Compromise |
| **AML.T0015** | Evade AI Model |
| **AML.T0054** | LLM Jailbreak |
| **AML.T0070** | RAG Poisoning — additional relevant current technique |

**Transcript correction:** The garbled supply-chain number **AML.T000010** should be **AML.T0010**. Names/IDs are subject to catalog updates; use the live [MITRE ATLAS](https://atlas.mitre.org/) when precise attribution matters.

**Framework distinction:** OWASP names a *risk*; ATLAS describes *adversary behavior that exploits it*. Use both when threat-modeling and planning detections.

### 4.3 NIST AI RMF

The **NIST AI Risk Management Framework (AI RMF)** is voluntary and uses four connected functions:

- **GOVERN:** Accountability, risk culture, responsibilities, policies and oversight.
- **MAP:** Identify use context, affected people, assets, hazards, threats and potential consequences.
- **MEASURE:** Evaluate quality, robustness, privacy, security, bias, reliability and control effectiveness.
- **MANAGE:** Prioritize and implement risk treatments; monitor outcomes and adapt.

**Govern underpins the other three** rather than being merely a phase that ends. The **NIST AI 600-1 Generative AI Profile** contextualizes the framework for generative-AI risks.

**Example:** A chatbot will process protected documents. **MAP** the user roles, flows and leakage threats. **MEASURE** leakage and unauthorized retrieval using tests. **MANAGE** through per-user authorization and monitoring. **GOVERN** by assigning ownership, review and evidence expectations.

### 4.4 ISO/IEC 42001 and complementary standards

**ISO/IEC 42001:2023** specifies an **AI management system (AIMS)**: policies, assigned responsibilities, objectives, impact/risk processes, monitoring, audit and continual improvement. It is a management-system standard that organizations may seek certification against; it is **not** an attack catalogue.

Other important backgrounds:

- **NIST CSF 2.0**: General cybersecurity functions **Govern, Identify, Protect, Detect, Respond, Recover**.
- **ISO/IEC 27001**: Information-security management systems, complementary to AI management requirements.
- **NIST SSDF / SP 800-218**: Secure Software Development Framework for software and build/dependency security, applicable to AI code and MLOps.

**Memorize the choice:** OWASP = *risk list*; ATLAS = *attacker methods*; NIST AI RMF = *risk-management activities*; ISO 42001 = *auditable management system*.

## 5. AI lifecycle and data security

### 5.1 Seven secure lifecycle gates

Rick emphasizes that **security starting only at deployment is too late**: the data, model and build process may already be compromised.

| Gate | Security questions | Controls | Evidence to retain |
|---|---|---|---|
| **1. Source data** | Who produced it? Is use permitted? | Approved sources, provenance, license and sensitivity review | Source register, dataset card |
| **2. Prepare data** | Were cleaning, transformations and labels altered? | Validation, label review, integrity checks, reproducible transformations | Version, checksums, labeling audit |
| **3. Train/tune** | Who can modify weights, code and environment? | Segregated training, least privilege, protected artifacts, change logging | Approved configuration, access logs |
| **4. Evaluate** | Is the model accurate, robust, fair, privacy-aware and safe enough? | Independent tests, adversarial evaluation, acceptance threshold and **release veto** | Test results, signed acceptance or rejection |
| **5. Deploy** | Can a user or agent do more than authorized? | Auth, least-privilege, gateways, secure inputs/outputs, fail-closed controls | Configuration, access rules, test evidence |
| **6. Monitor** | Has behavior, data, access or costs changed? | Drift checks, unusual-query detection, leakage and cost monitoring | Metrics, alerts, incident records |
| **7. Retire** | Are data, weights, endpoints, credentials and dependencies disposed of appropriately? | Revoke access, disable APIs, secure deletion according to retention requirements | Decommission and retention record |

**Evaluation must be an actual gate:** If a model fails required robustness, privacy, reliability or safety tests, there must be a means to **block promotion**. Reporting a red metric without stopping release is weak control design.

### 5.2 Five key data properties

**Provenance**: Verified origin and history of the data, including source, chain of custody and transformations. *Where did it come from? What happened to it?*

**Quality**: Accuracy, completeness, timeliness and representativeness. *Does it correctly describe the intended reality?* A legitimate source can contain poor-quality data.

**Label integrity**: Confidence that supervised-learning labels were assigned and preserved correctly. Use trusted labelers, sampling, review and audit trails.

**Privacy**: Personal and protected information should not be unnecessarily trained on, disclosed or retained. Consider collection permissions, de-identification, access controls and the risk of memorized content.

**Minimization**: Only collect, use, expose and keep information needed for an authorized purpose. Uncollected data cannot later be leaked by that workflow.

**Data lineage (background)** records the flow of datasets through transformations. It overlaps with **provenance**, which emphasizes verifiable source and custody. Both are valuable for incident investigation.

### 5.3 Minimal data card for each dataset

| Field | Record |
|---|---|
| Identifier/version | Exact dataset and release |
| Source / publisher | Who supplied it, acquisition date and approval |
| License and rights | Permitted training, retention, sharing and commercial use |
| Owner | Responsible business and technical contacts |
| Sensitivity | Classification and personal-data risks |
| Transformations | Cleaning, filtering, merging and label changes |
| Integrity | Expected cryptographic hash and trusted signature if available |
| Validation | Quality, outlier, duplication and privacy checks |
| Retention | Keep/delete requirements and decommissioning plan |

**A checksum verifies byte equality**, not trust in the original publisher. Combine hashes with trusted provenance/signatures and organizational review.

### 5.4 Secure by design for AI

**Secure by design** means security requirements and controls are chosen at the start of the AI lifecycle, not patched onto the final chatbot as an afterthought.

1. Document business objective, authorized users, unacceptable impacts and responsible owners.
2. Threat-model **data sources**, training, model, inference and connected tools.
3. Validate sources, labeling, provenance, licensing and privacy.
4. Restrict who can change datasets, code and weights.
5. Require evaluations that can reject release.
6. Enforce independent runtime policy and least-privilege tool permissions.
7. Monitor drift, abnormal prompts, leakage, errors and financial cost.
8. Control changes and plan eventual retirement.

**Drift (background)**: A change in incoming data distribution (**data drift**) or in relationships being predicted (**concept drift**). Drift may reduce model accuracy without any attacker, but it must still be monitored.

## 6. Adversarial machine learning

This section concerns **attacks against an already trained model**, typically through inference, not corruption of its training dataset.

### 6.1 Why attacks can work

A classifier divides possible inputs into regions separated by **decision boundaries**. A carefully crafted change to an input may cross a boundary and produce an incorrect prediction, even though the input looks unchanged to a human. Researchers can exploit **gradients** where available, or infer behavior through repeated **queries**.

- **White-box attack (background)**: The attacker can inspect or knows internal details, perhaps the weights or gradients.
- **Black-box attack (background)**: The attacker primarily sends inputs and observes outputs. The inference API becomes an experimental tool.
- **Adversarial example**: Input purposely crafted to cause a particular model mistake.

An attacker may send an input, observe a classification/confidence, revise the input, and repeat. A query API with unrestricted access and detailed confidence scores can make these attacks easier.

### 6.2 Four attacks to distinguish

| Attack | What the attacker wants | Mechanism | Main CIA impact |
|---|---|---|---|
| **Evasion** | Make a validly trained model classify one input incorrectly. | Slightly change input to cross a decision boundary (e.g., a modified malware sample wrongly classified as benign). | **Integrity** |
| **Model extraction / stealing** | Recreate the model's behavior or obtain its valuable intellectual property. | Repeated queries and outputs used to train a substitute model; or artifact theft by other means. | **Confidentiality / IP** |
| **Model inversion** | Recover information resembling training records or sensitive attributes. | Use output patterns or confidence information to reconstruct features. | **Confidentiality** |
| **Membership inference** | Determine whether a **specific record** was in the training data. | Exploit differences between outputs for member and non-member records. | **Confidentiality / privacy** |

**The four one-sentence distinctions:**

- **Evasion**: *Can I make this intact model give the wrong answer now?*
- **Extraction**: *Can I copy or reconstruct the model?*
- **Inversion**: *What can I infer about the data it learned from?*
- **Membership inference**: *Was this record in its training set?*

**Example:** If a medical model exposes whether a person was included in a highly sensitive research dataset, simply learning the answer **yes/no** can disclose private information, even without reconstructing an entire health record.

### 6.3 Defenses against each family

| Attack | Relevant defenses | Important limit |
|---|---|---|
| Evasion | Adversarial training, robustness tests, preprocessing where appropriate, ensembles, review of important decisions. | No universal defense; attack and defense methods evolve. |
| Extraction | Authenticate callers; enforce per-user quotas; monitor large-scale probing; minimize unnecessary output detail. | Distributed/low-query attacks may still succeed. |
| Inversion | Limit detailed response signals, control API access, assess privacy, consider privacy-preserving learning. | Coarse labels do not guarantee privacy. |
| Membership inference | Privacy tests, data minimization, differential privacy when suitable, rate limits, restricted output and monitoring. | Differential privacy requires careful implementation and a measured privacy budget. |

**Output minimization**: Return only what the business task needs. If a label is sufficient, there may be no reason to expose all class probabilities, logits, debug traces or internal gradients.

**Differential privacy (background)**: A mathematical approach that reduces how much published model results can reveal about any one training record, often by adding calibrated noise. It is a specific privacy guarantee under stated assumptions, **not** a universal guarantee against all data disclosure.

**Monitor the inference API:** Authentication/authorization, rate limits, quotas, high-volume querying, unusual systematic input patterns, response-size limits and suspicious attempts to infer model boundaries. Protect logs from becoming another source of sensitive-data leakage.

**Framework connection:** Evasion concerns integrity; extraction/inversion/membership largely concern confidentiality. MITRE ATLAS **AML.T0024** describes exfiltration through model inference interfaces; OWASP's sensitive-disclosure risk also applies.

## 7. Direct prompt injection, jailbreaks, and system-prompt leakage

### 7.1 Why a language model can be redirected

The model can be given high-priority instructions and lower-priority user input within a common context. Models and APIs may distinguish message roles, but this is **not a reliable security isolation boundary**. The model processes text that may include attacker-written instructions and can sometimes mistake that text for instructions it should follow.

**Prompt injection**: Crafted input that induces an LLM to follow attacker-controlled instructions in conflict with the application's intended rules or use.

**Direct prompt injection**: The attacker deliberately places the instruction in the user-controlled prompt or message sent straight to the application.

**Jailbreak**: An attempt to bypass safety restrictions. It may use prompt injection, but the distinguishing **goal** is to obtain output the model would normally refuse.

**System-prompt leakage**: The model reveals all or part of its internal system/developer prompt. This can expose business rules, tool names, internal assumptions or mistakenly stored secrets.

| Phenomenon | Delivery or goal | Typical clue |
|---|---|---|
| **Direct injection** | Attacker controls prompt directly. | User requests instructions contrary to trusted requirements. |
| **Indirect injection** | Attacker embeds instructions in a retrieved page, email, PDF, document or tool response. | Ordinary user's request is benign, external content is hostile. |
| **Jailbreak** | Bypass safety policy/guardrails. | Role-play, fake authority, or obfuscated request to produce refused content. |
| **Prompt leakage** | Extract internal prompt content. | Model is induced to describe hidden rules/configuration. |

### 7.2 Attack patterns to recognize

- **Override**: A statement claiming previous instructions should be ignored.
- **Authority spoofing**: Text falsely claiming to be system, developer or administrator authority.
- **Role play**: Convincing the model to simulate a persona supposedly outside its restrictions.
- **Obfuscation**: Encoding, splitting, paraphrasing or formatting malicious intent to evade simple screening.
- **Disclosure request**: Attempts to reveal hidden prompts, credentials or privileged context.

Keyword blocklists cannot enumerate all possible ways to express an adversarial instruction.

### 7.3 Comparison with SQL injection (IT-security prerequisite)

**SQL injection** occurs when untrusted text becomes executable database-query syntax. **Parameterized queries** separate SQL code structure from user-provided values.

Prompt injection is analogous because content crosses a **data-to-instruction trust boundary**, but there is no equally complete, general-purpose equivalent of SQL parameterization for all LLM behavior. Models can be trained to follow instruction hierarchies; that helps but is not sufficient alone.

### 7.4 Defense in depth

1. **Input/output screening and guardrail models**: Detect suspicious prompts or leaked information. Useful but probabilistic; can fail.
2. **Clear instruction hierarchy and delimiters**: Use proper trusted roles and distinguish retrieved material from developer instructions. Helpful but not authorization.
3. **Least privilege and limited context**: Expose only necessary data and tools. Never give a summarization assistant powerful administrative capabilities without need.
4. **No secrets in system prompts**: Consider prompt text potentially discoverable. Store credentials in a secured secrets manager.
5. **Independent enforcement**: A policy engine validates **who** requests **which action** on **which resource**, including destination, classification and business rules.
6. **Human approval**: For high-impact deletion, sending protected material, granting permissions or financial actions, require explicit approval.
7. **Logging and red-team testing**: Log necessary events and tool decisions while masking protected content; test adversarial prompt variations.

**Most important architecture rule: The model proposes; a trusted control decides.** If model output requests sending an email or exporting records, an independent, deterministic control must authorize the exact action. An extra sentence in the prompt is not a sufficient guarantee.

**[Background] Least privilege**: Give an identity, service, tool or model only the necessary capabilities. **Secrets manager**: Dedicated service that stores and issues sensitive credentials with controlled permissions, rotation and auditing.

**Framework connection:** Rick uses **OWASP 2025 LLM01** for prompt injection and **LLM07** for system-prompt leakage; MITRE ATLAS **AML.T0051** represents LLM prompt injection.

## 8. Indirect prompt injection, RAG, and output handling

### 8.1 The threat is in the material being read

In **indirect prompt injection**, a normal user asks a legitimate question but the model later reads attacker-controlled content in:

- A PDF, résumé, wiki page, internal knowledge article or email.
- Search results or a web page.
- A third-party API/tool response, including text values in JSON.
- Comments in source code.
- Documents stored in a retrieval index.

**Example:** A résumé contains small hidden text instructing a hiring assistant to rank its applicant first. The malicious instruction comes **from the document**, not from the legitimate user. A similar payload can ask a privileged assistant to send files to an external address.

The attack is harder to spot because the user's message may be innocent; the hostile content could have been indexed months earlier or controlled by a third party.

### 8.2 RAG explained

**Retrieval-Augmented Generation (RAG)**: The application searches for external documents relevant to a user request, places selected passages into model context and uses the model to compose an answer. **Ordinary RAG does not retrain the model weights.**

**Basic path:** Authenticated user → search/retrieval → document chunks → prompt/context → model response → output consumer/tools.

**Embedding (background)**: A numerical representation of a document or text passage that helps measure semantic similarity. **Vector store (background)**: Database/index supporting similarity search over embeddings.

RAG introduces both new functionality and new controls:

1. **Source provenance**: Who created or modified each document or chunk?
2. **Retrieval authorization**: Is the requesting user allowed to see each returned chunk?
3. **Index integrity**: Can an unauthorized actor alter indexed material?
4. **Instruction handling**: Will the assistant treat retrieved text as data, not trusted commands?
5. **Response authorization**: Will citations and answers reveal content outside the user's entitlement?

**Critical design rule:** A backend service account with access to all enterprise documents must **not** cause the assistant to expose all those documents to every user. Authorization must reflect the actual requesting user's rights, including at retrieval and tool-action boundaries.

### 8.3 Improper (insecure) output handling

**Model output is untrusted input to the next system.** It may contain attacker-controlled text from malicious prompts, documents or tool responses.

| Downstream consumer | Unsafe behavior | Traditional vulnerability / control |
|---|---|---|
| Web browser | Render generated HTML or script as executable code. | **XSS**: use context-specific output encoding and safe rendering. |
| Database | Concatenate generated strings into SQL. | **SQL injection**: parameterized queries and restricted database permissions. |
| Shell/interpreter | Directly execute generated commands or code. | **Command/code injection**: do not execute untrusted text; restrict to typed, allowlisted operations. |
| API/tool | Treat generated action as automatically authorized. | **Excessive agency / unauthorized action**: independent policy and approval. |
| Another model/agent | Relay content as if it were a trusted instruction. | Maintain trust/provenance and policy at every hop. |

**Cross-Site Scripting (XSS) — background**: Malicious script executes in another user's browser when a website renders unsafe content.

**Output validation** checks type, format, range, schema and business constraints. **Output encoding** converts content for a specific destination context so that text is not interpreted as active code. The two are related but **not interchangeable**.

### 8.4 Example full attack chain

1. An attacker adds malicious instructions to a document.
2. The application's RAG retrieves that document for a legitimate query.
3. The model incorporates the attacker's instruction into its output.
4. The application uses the output in an unsafe downstream operation.
5. The resulting browser, database, shell or tool misbehaves.

This can combine **prompt injection at the input edge (2025 OWASP LLM01)** with **improper output handling at the output edge (2025 OWASP LLM05)**.

### 8.5 Controls for both edges

**Input edge:** Trusted/approved sources, per-document and per-user permissions, provenance tags, sanitation appropriate to the use case, minimized context, segregation of content from instructions, and adversarial document tests.

**Output edge:** Strong type and schema validation, destination-appropriate encoding, parameterized SQL, no arbitrary shell execution, independent authorization for tool calls, constrained permissions, and human review of consequential decisions.

**Across both:** Log relevant retrieval sources, user identity, actions requested and decisions made. Minimize sensitive data stored in logs; protect and retain them under an explicit policy.

**Exam distinction:** A retrieved PDF telling the model to change its behavior is **indirect prompt injection**. A model's resulting script being blindly executed by a browser is **improper output handling**. Both may occur in the same incident.

## 9. Data poisoning, backdoors, and RAG-index poisoning

### 9.1 Training-data poisoning

**Data poisoning** is deliberate corruption of the data a model learns from through insertion, alteration, removal or mislabeling of examples. The algorithm may be functioning as designed: it simply **learns from dishonest data**.

Possible entry points: public datasets, scraped content, user-contributed examples, labeling contractors, feedback loops, reward data and fine-tuning collections.

### 9.2 Two objectives of poisoning

| Type | Objective | Detectable symptom |
|---|---|---|
| **Targeted poisoning** | Cause one chosen class, identity or trigger pattern to fail, while the model otherwise works. | Overall accuracy can remain high; narrow failures may go unnoticed. |
| **Availability poisoning** | Damage accuracy or usefulness broadly for many users. | General degradation or unreliable predictions. |

**Do not confuse availability poisoning with inference-time denial of service:** one degrades the learned model, the other overwhelms its running service.

### 9.3 Model backdoors and Trojans

A **backdoored model** performs normally until a hidden **trigger** appears; then it produces an attacker-chosen result. The backdoor may be introduced through malicious training examples, fine-tuning or tampered weights.

Triggers could be a small visual patch, special phrase, rare token or unusual input feature. Ordinary testing may never exercise that trigger. High overall accuracy is therefore **not** proof the model has no backdoor.

**Targeted poisoning and backdoors** are closely related; a trigger-based backdoor is a particularly stealthy targeted outcome.

### 9.4 Fine-tuning poisoning

Many organizations do not train the foundation model themselves. They adapt a trusted base model using smaller datasets or adapters. A compromised tuning dataset can alter behavior or add a backdoor **after** base-model acquisition.

**Controls:** Vet tuning data, audit labeling, version adapters, restrict training access, compare behavior to the base model and run targeted evaluation before promoting the tuned model.

### 9.5 RAG/index poisoning versus indirect prompt injection

A malicious document can poison a retrieval system **without changing the base model's weights**.

- **RAG knowledge poisoning:** Attacker inserts false information that the model uses as evidence. The resulting answer is incorrect because the source material is false.
- **Indirect prompt injection:** Attacker inserts instructions that ask the model to ignore rules, disclose data or take unauthorized action.

The same document may contain **both** malicious facts and instructions. Distinguish *corrupting what the model knows from retrieval* from *commanding what it should do*.

### 9.6 Defense-in-depth against poisoning

1. **Source vetting**: Approve and authenticate data providers, publishers and labels.
2. **Provenance/integrity**: Track who supplied every dataset and document and which transformations occurred.
3. **Validation**: Quality checks, duplicate analysis, outlier checks, label review and sampling. Sophisticated poison may not be statistically abnormal.
4. **Pipeline protections**: Restricted changes to learning data, tuning jobs and models; reproducible and audited releases.
5. **Evaluation gates**: Model quality, robustness, privacy, bias and targeted trigger checks. Require approval before deployment.
6. **Index controls**: Permissioned ingestion, protected retrieval indexes, version history and monitoring of document changes.
7. **Response**: Quarantine affected data/model versions, rebuild from known-good sources, evaluate affected outputs and document the incident.

**Framework connection:** In Rick's 2025 OWASP mapping, **LLM04** covers data/model poisoning; MITRE ATLAS **AML.T0020** describes training-data poisoning.

## 10. AI supply-chain security and AI-BOM

### 10.1 What is the AI supply chain?

Modern AI solutions depend on components the team often did not create:

**Datasets and labeling vendors → base models and weights → tuning adapters → ML frameworks and libraries → model hubs/registries → deployment pipelines → plugins and MCP servers → applications.**

**Transitive trust**: Using one component implicitly relies on its upstream sources and dependencies. A popular hub download or a professional-looking model card is **not security verification**.

### 10.2 Four headline risks

| Risk | Example | Key controls |
|---|---|---|
| **Tampered weights/model files** | Downloaded artifact differs from approved publisher release. | Cryptographic integrity/signatures, trusted source, exact version pinning. |
| **Malicious or Trojaned models** | Model behaves deceptively under a trigger, or loading the file executes code. | Vetting, safe loading, artifact scanning, isolated test environment. |
| **Typosquatted dependencies** | Attacker publishes a package whose name resembles a common ML library. | Approved registries, exact names, pinned dependencies, SCA. |
| **License and data-rights traps** | Model/data license forbids the intended use or source lacked usage rights. | Licensing review, provenance, approvals and documentation. |

### 10.3 Why a model file may be executable

**Serialization (background)** encodes a model/object into a file; **deserialization** loads it. Some serialization formats or loaders permit code execution during loading. Untrusted model artifacts must **not** be assumed to contain harmless numerical weights only.

Use safer non-executable formats when possible, disable unreviewed custom code, scan artifacts and load new models in restricted environments. Validate vendor identity and exact artifact integrity **before** deployment.

### 10.4 Provenance, hashing, signatures, scanning and pinning

- **Model provenance**: Document who created/published it, its source, base model, training/tuning lineage, rights, version, known limitations and custody.
- **Hash/checksum**: Detect whether bytes match an expected value. It **does not** prove a malicious publisher was trustworthy.
- **Cryptographic signature**: Verifies a trusted signing key attested to specified bytes; check key trust and context.
- **Scanning**: Inspect artifacts, dependencies and containers for known weaknesses, suspicious structures and unsafe packages.
- **Version/hash pinning**: Fix approved model, dataset, package and dependency versions so builds cannot silently upgrade.
- **Release approval**: Only verified, tested artifacts move from development to production.

**Typosquatting (background)**: Publishing a misleadingly similar dependency name to trick developers into installing a malicious package. **SCA (Software Composition Analysis)** inventories dependencies and identifies known vulnerabilities or license issues.

### 10.5 AI-BOM versus SBOM

**SBOM — Software Bill of Materials**: Structured inventory of software libraries and dependencies.

**AI-BOM — AI Bill of Materials**: Extends the inventory to AI models, versions/weights, training/tuning datasets, libraries, external model services, plugins and related artifacts.

| AI-BOM attribute | Why track it? |
|---|---|
| Component/model/dataset name | Identify affected assets. |
| Exact version and hash | Identify exactly what is deployed. |
| Publisher/source/license | Establish provenance and usage rights. |
| Owner and linked services | Assign remediation responsibility. |
| Dependencies and approved environments | Understand downstream blast radius. |
| Evaluations and approval dates | Prove release acceptance and detect changes. |

**Why it matters:** If a model or dependency is disclosed as compromised tomorrow, an AI-BOM helps determine **whether you use it, where, which version, and who must respond**.

**Response example:** Search AI-BOM for compromised version → identify dependent services → block new deployment and isolate affected copies → verify hashes and logs → replace/rollback → re-evaluate → record incident and follow-up.

### 10.6 Third-party tools and MCP

An assistant may connect to external APIs and tools, including **MCP servers**. **Model Context Protocol (MCP — background)** defines an interface for connecting AI applications with resources and tools. These integrations may have read/write, network or file privileges and need normal software-supply-chain, identity and authorization review.

**Supply-chain review question:** Who wrote this tool, what can it access, how is it authenticated, which scopes can it exercise, and how will we notice an unauthorized update?

**Framework connection:** **2025 OWASP LLM03 = Supply Chain**; **MITRE ATLAS AML.T0010 = AI supply-chain compromise**; NIST SSDF offers relevant secure-development practices.

## 11. Putting it together: secure enterprise assistant

> [!note] Added application example
> This is an original enterprise scenario to connect the lessons. It is not a claim that episodes 00–09 cover every detail of secure architecture; Rick plans to cover that more directly in episode 10.

### 11.1 Use case and design

A department provides an assistant to answer employees' questions using internal documents. Documents have different sensitivity levels and user permissions. The assistant can propose service tickets but must not independently export records, delete files or change access rights.

**Preferred high-level data path**:

1. **Authenticate the user** and obtain the user's actual roles/attributes.
2. **Check authorization** for the requested action and document scope.
3. **Retrieve only documents the user may access**; attach source identifiers/classification.
4. **Treat retrieved passages as untrusted content**, not commands.
5. **Generate a draft answer** with permitted source references.
6. **Validate and safely render the output**; avoid exposing protected details.
7. For any requested action: **send the model's proposal to a deterministic policy check**, require review for consequential operations, then call a restricted tool.
8. **Monitor** access, query patterns, error rates, leakage tests and cost; preserve audit evidence proportionately.

**Architecture formula:**

**User identity → policy-controlled retrieval → provenance-tagged context → LLM → output checks → independently authorized tools → audit/monitoring.**

### 11.2 Map threats onto this design

| Threat | Failed boundary | What to implement |
|---|---|---|
| Unauthorized worker asks for protected content | User identity → retrieval | Enforce resource permissions for the actual user; filter results before sending them to model. |
| Poisoned document attempts to send records | Retrieved content → model → tools | Restrict the model's authority; enforce separate, typed tool policy and review exports. |
| Web result contains fabricated policy instructions | External source → RAG evidence | Trusted source ranking/provenance, cross-check facts and testing. |
| Model output contains HTML/script | Model output → browser | Safe renderer and context-specific output encoding. |
| Agent requests a destructive operation | Generated proposal → privileged API | Independent authorization, allowlisted operations, human approval if significant. |
| Public package changes without review | Third-party dependency → production | Pin versions, verify signatures/hashes, scan and approve releases. |
| Training data includes unauthorized confidential records | Data collection → training | Rights, classification, minimization, controlled datasets, privacy evaluation. |
| High-volume queries reveal model behavior | Public API → inference | Auth, quotas, response minimization, monitoring and privacy testing. |
| Abusive requests produce large bills | Gateway → compute budget | Token limits, query quotas, cost budgets, concurrency limits and alerts. |

### 11.3 How to write a security risk statement

Use a repeatable structure:

**Because [actor/source] can influence [component] at [stage], the system may [undesired behavior], resulting in [CIA and business impact]. We mitigate with [controls] and verify them through [tests/evidence].**

Example:

> Because an external PDF can influence the retrieval context during inference, the assistant might treat attacker-written text as a command, resulting in unauthorized document disclosure. We mitigate this with per-user retrieval permissions, tool least privilege, independent export authorization, restricted network destinations and adversarial-document testing. Effectiveness is verified through repeatable tests and protected audit records.

### 11.4 Twelve questions a security reviewer must ask

1. What legitimate business decisions is the AI system permitted to support?
2. Who owns the model, dataset, policy decisions and residual risk?
3. Which sources, vendors, models and packages can influence it?
4. Where can untrusted text enter a prompt or retrieval context?
5. What information classification and data-minimization requirements apply?
6. Does retrieval honor the *requesting user's* permissions?
7. What are the model's and agent's actual tool, network and file privileges?
8. Can a model-generated response cause a privileged action without independent checks?
9. Are output consumers protected from HTML, SQL, shell and other injection?
10. What tests must pass before model/data/prompt or dependency changes ship?
11. What telemetry detects abnormal queries, extraction, drift, data leakage or costs?
12. How are compromised artifacts quarantined, access revoked and systems retired?

## 12. Attack-to-control reference table

This is the table to review before quizzes, design reviews and exam scenarios.

| Threat / failure | Stage | Principal impact | Recognize it by | Primary control categories |
|---|---|---|---|---|
| Data/label poisoning | Training data | Integrity | False or altered learning examples | Trusted sources, provenance, label checks, eval gates |
| Targeted poisoning | Training | Integrity | Failure only for selected targets | Targeted tests, training-data review |
| Availability poisoning | Training | Availability / integrity | Broad model degradation | Data validation, evaluation and trusted rebuild |
| Backdoor/Trojan model | Training/tuning/artifact | Integrity | Hidden trigger changes output | Trusted artifacts, trigger tests, signed deployment |
| Evasion | Inference | Integrity | Crafted input fools intact classifier | Adversarial robustness, review, monitoring |
| Model extraction | Inference or artifact | Confidentiality / IP | Attacker clones model from responses | Auth, output limits, quotas, monitor access |
| Model inversion | Inference | Confidentiality | Reconstruct characteristics of training inputs | Data/privacy controls, output/query limits |
| Membership inference | Inference | Confidentiality | Determine specific training-set membership | Privacy testing/training, output/query restrictions |
| Direct prompt injection | User input | Integrity / confidentiality | Attacker sends conflicting instructions | Least-privilege tools, guardrails, independent policy |
| Indirect prompt injection | External content/RAG | Integrity / confidentiality | Attack is hidden in retrieved content | Trust tagging, retrieval ACLs, restricted tools |
| Prompt leakage | Inference output | Confidentiality | Internal prompt/rules disclosed | No prompt secrets, restricted capabilities |
| RAG knowledge poisoning | Ingestion/retrieval | Integrity | False source information drives wrong answer | Protected index, provenance, source validation |
| Improper output handling | Downstream application | Integrity / confidentiality | Generated string passed unsafely to consumer | Output encoding, schema checks, parameterized queries |
| Malicious model package | Supply chain | CIA varies | Third-party artifact runs malicious code | Trusted publisher, hash/signature, scanning, isolation |
| Typosquatting | Software dependencies | CIA varies | Similar-looking package name | Approved package registry, pinning and SCA |
| Excessive agency | Agent/tool integration | CIA varies | Model may call tools with broad powers | Scopes, least privilege, deterministic policy and approval |
| Unbounded consumption | Inference gateway | Availability / cost | Long or repeated costly queries | Quotas, token limits, cost and concurrency control |
| Hallucination/misinformation | Inference/decision | Integrity | Convincing output unsupported by evidence | Grounding, corroboration, human decision review |

**First-response rule:** Answer *where the attack lives*, then choose a control that enforces the relevant **trust boundary**. A stronger prompt may help, but cannot replace authorization, validated outputs or model/data integrity.

## 13. IT security basics: concise glossary

> [!note] Prerequisite background
> These short definitions are included because Rick assumes prior IT/cybersecurity experience. You do not need to memorize a textbook chapter for each term; understand the term and be able to explain its relevance to an AI scenario.

### 13.1 Core security vocabulary

| Term | Definition / relevance |
|---|---|
| **Asset** | Something valuable requiring protection: model, data, service, credentials or reliable business decision. |
| **Threat** | Potential cause of unwanted security impact. |
| **Vulnerability** | Weakness an attacker or event can exploit. |
| **Exploit** | Technique that leverages a vulnerability. |
| **Risk** | Uncertainty about harm and its consequences, often assessed by likelihood and impact. |
| **Threat modeling** | Structured identification of assets, entry points, adversaries, failures and controls. |
| **CIA triad** | Confidentiality (no unauthorized disclosure), Integrity (no unauthorized alteration), Availability (usable when needed). |
| **Least privilege** | Give only minimal permissions required for a specific function. |
| **Defense in depth** | Combine complementary safeguards rather than trusting a single layer. |
| **Fail closed** | Deny access/action if a necessary safety or authorization decision cannot be made. |
| **Zero Trust** | Do not trust merely because an entity is inside a network; verify identity, conditions and authorization per resource/action. |
| **Compensating control** | Alternative safeguard used when a preferred control cannot be applied. |
| **Residual risk** | Risk remaining after controls are implemented. |

### 13.2 Identity, authorization and API access

| Term | Definition / relevance |
|---|---|
| **Authentication (AuthN)** | Verifying who/what a caller is. |
| **Authorization (AuthZ)** | Determining the actions/resources an identity is permitted to use. **AuthN ≠ AuthZ.** |
| **IAM** | Identity and Access Management: accounts, roles, credentials and policy. |
| **RBAC** | Role-Based Access Control; permissions granted through assigned roles. |
| **ABAC** | Attribute-Based Access Control; decisions based on user, action, resource and context properties. |
| **MFA** | Multi-Factor Authentication using independent factor categories. |
| **Service account** | Non-human identity used by a service; should have strictly scoped privileges. |
| **Access token / API token** | Credential granting specified access; scope, expiry and secrecy matter. |
| **OAuth 2.0** | Framework for delegated authorization. It is **not itself** an authentication protocol. |
| **OpenID Connect (OIDC)** | Authentication/identity layer built on OAuth 2.0. |
| **API gateway** | Service entry point for authentication, policy enforcement, routing, quotas and logging. |
| **Rate limiting** | Limit how frequently a client can make requests. |
| **Quota** | Usage allowance for a time period, such as calls or tokens per day. |

### 13.3 Information protection and cryptography

| Term | Definition / relevance |
|---|---|
| **Encryption at rest** | Encryption protecting stored information. |
| **Encryption in transit / TLS** | Encryption and integrity protection for data moving across connections. |
| **Encryption in use** | Specialized protection of data during processing, where supported. |
| **Key management** | Creation, storage, access, rotation, revocation and disposal of cryptographic keys. |
| **Hash / checksum** | Digest for detecting change, not reversible encryption; equality is not proof of origin. |
| **Digital signature** | Cryptographic attestation of integrity associated with a signing key; requires a trust decision about the key. |
| **Data classification** | Labeling information by sensitivity and handling requirements. |
| **Redaction** | Removing or obscuring sensitive information in a document or output. |
| **Masking** | Hiding selected parts of a displayed value. |
| **Pseudonymization** | Replacing direct identifiers; individuals may still be re-identifiable. |
| **Anonymization** | Transformation intended to prevent identification, subject to strong assessment. |
| **Data minimization** | Collect, expose and retain no more than necessary. |
| **Data provenance** | Verifiable record of source and custody. |
| **Data lineage** | Record of transformations and flow through a data system. |

### 13.4 Application and supply-chain security

| Term | Definition / relevance |
|---|---|
| **Input validation** | Ensure inputs satisfy allowed structure, types and business constraints. |
| **Output encoding** | Render data safely for its destination (HTML, database, etc.) so it is not interpreted as code. |
| **SQL injection** | Untrusted text is interpreted as SQL commands. Use parameterized queries. |
| **Cross-Site Scripting (XSS)** | Untrusted script executes within a victim's browser via a website. |
| **Command injection** | Untrusted text becomes an operating-system or interpreter command. |
| **CVE** | Identifier assigned to a publicly disclosed vulnerability; different from an attack technique ID. |
| **CI/CD** | Continuous integration and delivery/deployment: automated build, test and release. |
| **MLOps** | Operational lifecycle for ML models and datasets, similar to DevOps but including learning/evaluation artifacts. |
| **SCA** | Software Composition Analysis; inventory of dependencies and known vulnerabilities/licenses. |
| **SBOM** | Software Bill of Materials, inventory of software components. |
| **AI-BOM** | AI Bill of Materials, expanded inventory including models, data and AI components. |
| **Serialization / deserialization** | Saving/loading program objects or models; unsafe loaders may execute malicious code. |
| **Typosquatting** | Deceptive package name meant to be mistaken for a trusted dependency. |

### 13.5 Monitoring, assurance and AI operations

| Term | Definition / relevance |
|---|---|
| **SOC** | Security Operations Center; detects, investigates and responds to incidents. |
| **SIEM** | Security Information and Event Management, collecting/correlating logs for detection and investigation. |
| **Telemetry** | Operational measurements, logs, traces and events. |
| **Anomaly detection** | Finding deviations from a defined or learned normal behavior. |
| **False positive** | Security alert or classification incorrectly marks an innocent case positive. |
| **False negative** | Failure to detect a true positive case or attack. |
| **Precision** | Fraction of positive detections that are actually correct. |
| **Recall** | Fraction of all real positive cases successfully detected. |
| **Overfitting** | Model learns training details too narrowly; may generalize poorly or increase privacy leakage. |
| **Red teaming** | Authorized adversarial tests of an organization's systems and defenses. |
| **Penetration testing** | Authorized exploitation-focused assessment of vulnerabilities. |
| **Guardrail** | Mechanism intended to reduce unsafe prompts, responses or model behavior. |
| **Model evaluation (eval)** | Repeatable assessment of accuracy, robustness, fairness, privacy, safety or task performance. |
| **Data drift** | Incoming data distribution changes from training/baseline conditions. |
| **Concept drift** | Relationship between input and target/outcome changes. |

### 13.6 AI-specific infrastructure and terms

| Term | Definition / relevance |
|---|---|
| **Token** | Unit used by a model to process text or other representations; contributes to resource usage and context. |
| **Context window** | Information the model can attend to in an interaction. |
| **System / developer prompt** | Higher-priority instructions configured by the application; not a secret vault or absolute security boundary. |
| **RAG** | Retrieval-Augmented Generation: model answers using externally retrieved context. |
| **Embedding** | Numerical representation of content for similarity or retrieval. |
| **Vector database** | Database that supports search using vectors/embeddings. |
| **Model inversion** | Recovering likely sensitive training-data attributes from model outputs. |
| **Membership inference** | Estimating whether a specific example was used in training. |
| **Adversarial example** | Input deliberately crafted to cause an incorrect model prediction. |
| **Backdoor / Trojan model** | Model designed to behave improperly when an attacker-selected trigger appears. |
| **Agent** | AI-enabled workflow capable of selecting and invoking tools to pursue tasks. |
| **MCP** | Model Context Protocol; integrates tools and data sources with AI applications. |
| **Human-in-the-loop** | Human reviews or authorizes certain AI-assisted decisions or actions. |
| **Shadow AI** | AI service/tool used without formal organizational approval or visibility. |
| **Data/model card** | Structured documentation of sources, usage, limitations, versions and tests. |

## 14. Clarifications and distinctions to memorize

Rick explains concepts effectively, but some transcript wording is simplified or distorted. Use these more precise distinctions:

| Simplified or confusing statement | Better understanding |
|---|---|
| **“You cannot patch a model.”** | You usually cannot edit learned behavior like ordinary source-code logic, but models **can** be retrained, fine-tuned, replaced, and surrounded by patched application controls. |
| **“All traditional software is deterministic.”** | Traditional programs can involve randomness/concurrency; controlled ML inference can also be deterministic. The key challenge is learned behavior. |
| **“LLMs cannot separate instructions and data at all.”** | APIs and training support role hierarchy, but **role hierarchy is not a hard authorization boundary**. |
| **“Output labels instead of probabilities prevent model extraction.”** | It may raise cost; attackers can still infer behavior from labels. Use several controls. |
| **“A checksum proves a model is trustworthy.”** | It only proves equality to a known digest, not that the original model was safe. |
| **“Good accuracy means no backdoor.”** | Triggered misbehavior may be invisible on normal test cases. |
| **“RAG poisoning changes model weights.”** | RAG usually changes the **retrieved context**, not weights. |
| **“Model inversion and membership inference are identical.”** | Inversion reconstructs features/content; membership asks whether a **specific** record was in training. |
| **“Prompt injection means the user typed a malicious prompt.”** | The attacker may instead poison a **document, webpage, email or tool response**. |
| **“Model output can be trusted because the model is ours.”** | Generated output is untrusted at every downstream interface; validate/encode it. |
| **“Prompt filters eliminate prompt injection.”** | They are probabilistic. **Independent policy and least privilege** limit damage when filters fail. |
| **“OWASP LLM IDs never change.”** | The **2025 and 2026** lists differ substantially; always include the year. |
| **“NIST AI RMF and ISO/IEC 42001 are the same.”** | AI RMF organizes risk functions; ISO 42001 specifies a management system that can be audited. |

**Spelling/transcription corrections**: **OWASP** (not “OASP”); **MITRE** (not “MITER”); **provenance** (not “providence”); **RAG** (not “RA”); **ISO/IEC 42001** (not “ISO 4201”); **SecAI+ CY0-001** (not the speech-to-text variations). **MITRE supply-chain technique AML.T0010**, not AML.T000010.

17. A vendor promises that a model-side prompt-injection filter is a complete cure. Why is that inaccurate?
18. An attacker sends deliberately expensive requests, producing an unexpectedly large inference bill. What risk category and which controls apply?
19. A system returns a confident but invented citation supporting a policy decision. What type of failure is occurring, and how should the organization treat it?
20. A model update performs worse after the team's data distribution shifts over time. There is no evidence of attack. Is this automatically poisoning?

### Answer key and reasoning

1. **Evasion at inference time**. A crafted input changes the output while the trained model remains intact. Use robustness evaluation and monitoring.
2. **Membership inference**. Presence in a sensitive training dataset can itself be private information.
3. **Model extraction**. Authenticate callers, limit query rate and detail, detect systematic probing; no one control makes theft impossible.
4. **Indirect prompt injection**. The hostile instruction came through retrieved content. Restrict tools/data and enforce independent authorization before exporting records.
5. **Improper output handling leading to XSS**. Use safe rendering and context-appropriate output encoding. One incident can involve both LLM01 and LLM05 in the 2025 list.
6. **Backdoor/Trojan with a hidden trigger**, often resulting from targeted poisoning or a tampered model artifact.
7. **Availability poisoning** in the model-performance sense, not an inference-time traffic flood.
8. **Fine-tuning poisoning/backdoor risk**. Validate the tuning dataset and repeat evaluation after adaptation.
9. **No.** False retrieved evidence is **RAG knowledge poisoning**. Indirect injection specifically involves untrusted content instructing the model to change behavior. Both can overlap.
10. **AI supply-chain compromise / unsafe deserialization**. Vet source, verify trusted hash/signature, scan, choose safer formats/loaders, isolate initial tests.
11. **Quality**. Documented origin does not ensure representative or correct content.
12. **MITRE ATLAS** maps adversary tactics and techniques; **NIST AI RMF** structures Govern, Map, Measure and Manage.
13. **ISO/IEC 42001**, an AI management-system standard.
14. It identifies **exact affected versions**, deployments, owners, dependencies and remediation targets.
15. **Excessive agency and privilege**. Prompts do not replace tool scopes, authorization policies and approval gates.
16. Apply **the employee's real permissions** before retrieving documents/chunks; never equate a backend service account's permissions with the end user's permissions.
17. Prompt screening is **probabilistic and can be bypassed**. Use least privilege, isolated data/tool access and independent deterministic action checks.
18. **Unbounded consumption / denial of wallet** affects availability and cost. Apply quotas, token/cost budgets, rate/concurrency limits, anomaly monitoring and alerts.
19. **Misinformation / hallucination and overreliance risk**. Require evidence checks, credible source grounding, and human review for consequential decisions.
20. **No.** It could be **data or concept drift**, ordinary quality problems or a process change. Investigate data, versions and source integrity before attributing malicious poisoning.
